# Lux 0.8 全量清单（1.0 冻结前的最后一个功能版）
先定调：按你们自己的 `stability.md` 破坏性变更窗口，**0.8.0 是最后一次允许破坏性变更的机会**（窗口只写到 0.8.0）。所以 0.8 的本质是：**把所有“1.0 之后做不了的事”全部做完**——破坏性语义迁移、最后的语法补齐、发布工程收尾。1.0 本身没有内容，只有冻结。
**前提假设**：A1（ARC）按 `arc.md` 的计划在 0.7.x 落地。如果滑档到 0.8，见文末的决策树。
---
## A. 主菜一：错误通道 A3（0.8 最重要的工作，也是最后一个破坏性窗口）
设计已在 `arc.md` §3，这里补落地细节和**三个设计文档里没暴露的问题**：
| # | 项 | 说明 |
| --- | --- | --- |
| A3.1 | ★ **`or` 关键字冲突必须先解决** | `arc.md` 草案用 `or` 做兜底（`read(p) or "default"`），但 **`or` 从 0.1 起就是 `\|\|` 的别名**！两个可行方案：(a) 按左操作数类型分派——bool 走逻辑或、`T?` 走兜底（JS `\|\|` 同款先例，无真歧义，但必须写进 grammar.md 优先级表）；(b) 新运算符 `??`。**选一个写死，别带歧义进 1.0** |
| A3.2 | 类型表示 | 建议 `TyKind::Optional`（复用 `elem` 字段），intern 化后指针相等依然成立——比 `tupleOf({bool,T,err})` 干净，`tyName()` 输出 `int?` |
| A3.3 | `?` 传播 + `name!` panic 变体 | 语法：类型位 `int?`、表达式后缀 `expr?`、panic 版本 `int!` / `read!`。注意 `!` 同时是一元逻辑非——`IDENT + '!' + '('` 的后缀位置无歧义，但 parser 要显式处理 |
| A3.4 | **标准库全量语义迁移**（隐藏成本最大的一步） | 逐个审计每个可能失败的函数：`int` `float` `read` `write?` `append?` `remove?` `rename?` `system?` `env?` `split`（空分隔符现在 panic——迁移成返回错误还是保留 panic？）`find`。每个函数给出终版签名表，这张表就是 stability.md 的附录 |
| A3.5 | 编译期校验 + 定向错误码 | 延续 `format_arity` 风格：`?` 用在非 `T?` 返回的函数里、`or` 左侧不是 `T?`、`!` 用在不会失败的函数上，各给专属 E 码，不落泛化“类型不匹配” |
| A3.6 | **迁移指南 + 诊断提示** | 0.8 起 `int("abc")` 不再返回 0——存量代码全炸。错误信息里要写明迁移路径（“0.8 起 int() 返回 int?；脚本场景请用 int!()，库代码建议 ? 传播”） |
| A3.7 | **测试套件自身的迁移** | 所有用了 `int(line)` / `read()` 的现存 `.expected` 都要重录；新增：`?` 传播链、`or` 兜底、`!` panic 路径、嵌套 `int??`、**三后端差分全覆盖** |
| A3.8 | REPL 跟进 | `println(x)` 遇到 `T?` 怎么显示（`some(42)` / `none`？）；补全词表加新运算符 |
## B. 主菜二：高阶函数 / `fn` 类型 B6
| # | 项 | 说明 |
| --- | --- | --- |
| B6.1 | `fn` 类型语法 | `fn(int, int) -> int` 进类型位（与 `fnOf` 工厂对应）。**1.0 边界要写死：只支持具名函数作为值，不支持 lambda/闭包**——写进 stability.md 的“不包含”，管理预期 |
| B6.2 | 函数作为值的运行时表示 | C 后端：按 `fnOf` intern 类型生成 typedef（仿 `structCName` 的 `fnCName`），函数名即指针；原生后端：取函数地址（lea label）压栈——两后端都要加一个“函数地址入槽”的发射原语，现有 8 字节槽约定直接兼容 |
| B6.3 | Sema 兼容规则 | **1.0 用严格相等**（intern 指针比较），不做变型/协变——文档写明。内置函数名（`abs` 等）能否作为值传递也要定（建议：可以，视为对应签名的函数值） |
| B6.4 | 标准库落地 | `sort(arr, cmp)`（稳定排序？文档写明）、`map(arr, f)`、`filter(arr, pred)`。返回新数组（与切片复制语义一致）。**注意 ARC 交互**：`map` 产出的 `string[]` 元素归谁？这是元素级 retain/release 的第一个真实压力测试 |
| B6.5 | 与 error channel 的组合 | `map(arr, parse_int)` 返回 `int?[]`——两个主菜在标准库里会相遇，测试要覆盖 |

## F. 1.0 冻结准备（0.8 收尾时的动作）
- `stability.md` 更新：错误通道、`fn` 类型、ARC 行为入“稳定承诺”；破坏性变更窗口改为“0.8.0 之后无”；
- “1.0 不包含”清单终审签字（泛型/map/无符号/并发/Windows/LLVM/闭包/包依赖解析）；
- 错误码全表（E0001~、W1001~W100x + 新增）整理成文档页——1.0 后这些码就是 API；
- 给 native 后端的诚实声明：1.0 无优化（栈机风格），性能预期由 E3 的实测数字管理。
## G. 明确不做（0.8 忌讳，在 0.7 基础上新增两条）
1. **lambda/闭包**——fn 类型只做具名函数值。闭包 = 捕获环境 = 另一个 ARC 交互雷区，1.x 再说；
2. **原生后端优化**——0.8 不碰代码生成质量，把精力留给正确性；
3. 继承 0.7 的：map<K,V>、泛型、并发、Windows。

## 顺序建议与决策树
```
0.7.x  C 层门槛清零（两枚真 bug 打头）+ A1 ARC 按 arc.md §4 落地
0.8.0  A3 错误通道（先定 or 冲突）→ B6 fn 类型 → D 层标准库收尾
0.8.x  E 层发布工程逐项上线 → F 层冻结准备
1.0.0  无内容，只有 stability.md 生效
```
**如果 ARC 滑档进 0.8**：二选一—— 0.8 只做 A1 + E 层，A3 顺延到 0.9，1.0 顺延； 或 1.0 照常冻结但**不带错误通道**（stability.md 的“不包含”里加一条）。**我强烈反对** A1+A3 塞进同一个版本——两者都触碰所有值传递路径，差分体系一次洗两次大澡，出问题时无法归因。宁可 1.0 晚一个季度，不要 1.0 带着一个仓促的错误通道。
最后一个判断：0.8 真正的风险点不是 A3 或 B6 的实现，而是 **A3.6/A3.7——语义迁移的爆炸半径**。每个用户的存量代码都会编译失败，你的诊断质量和迁移指南就是这门语言的第一次“大规模公关”。把那条 `0.8 起 int() 返回 int?，请用 ? 传播或 int!()` 的错误信息写好，它会被最多的人看到 ⌯˃̶᷄ ﹏ ˂̶᷄⌯
